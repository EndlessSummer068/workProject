# AGENTS.md — 行为规则（Agent/协作者必读）

> 本文件只管**行为**，不含技术与数值：技术约定一律引用 [docs/TECH.md](TECH.md)，玩法与数值一律引用 [docs/GAME.md](GAME.md)。

---

## 0. 每次开工必读（按顺序，缺一不写代码）

1. `docs/GAME.md` —— 玩法与数值的唯一来源
2. `docs/TECH.md` —— 技术约定的唯一来源
3. `AGENTS.md` —— 本文件
4. `BUILD_PLAN.md` —— 任务与验收的唯一来源

## 1. 行为规则（硬性）

- 一次只做 **BUILD_PLAN.md 中的一个任务**；未验收通过不开始下一个。
- 先读文档再动手：动数值先定位 GAME.md 节号，动实现先定位 TECH.md 节号。
- 禁止扩大范围：不做任务清单外的事、不顺手重构、不引入任何插件/addon、不修改无关文件。
- **禁止修改 docs/ 以外的既有数值**（balance.gd 常量、场景属性等）；若任务本身要求改数值，必须先改 GAME.md（顺序见 §2），再同步代码，并在交付说明中标注。
- GAME.md 标「待定」的内容可按其标注的提案实现，但必须在交付说明中重新列出。

## 2. 文档更新顺序（固定，不许倒置）

涉及玩法/数值/技术变化时，**全部改完才允许开始实现**：

1. 先改 `GAME.md` 对应小节（数值/规则，标注来源）；
2. 技术约定有变化才改 `TECH.md`（含文末映射表同步）；
3. 把本任务的**验收标准**写进 `BUILD_PLAN.md`；
4. 实现；
5. 结束时明确列出：本次改了哪些文档的哪些小节。

## 3. 完成定义（DoD）——四条全满足才能标"完成"

- (a) **项目能运行无报错**：编辑器运行无红字，或 `godot --headless --import` 退出码 0；
- (b) **贴出验收证据**：验收命令及其输出 / 截图 / 日志，与 BUILD_PLAN.md 中该任务的验收标准一一对应；
- (c) **文档已按 §2 顺序更新**；
- (d) **提交信息符合格式**：`[Pn][L01-xx] 一句话` —— Pn 与 L01-xx 前缀**原样取自 BUILD_PLAN.md 中该任务的编号**。

## 4. 失败处理

- 同一验收标准**连续失败 2 次**：立即停止，不得硬改。
- 停止后必须回报三件事：
  1. **卡在哪**：完整报错/异常现象；
  2. **试过什么**：每次尝试的做法与结果；
  3. **建议下一步**：基于证据的候选方案，交用户决策。
- 禁止：大规模删除重写、整体注释代码绕过报错、放宽或跳过验收标准。

## 5. 提交策略

- **一条 BUILD_PLAN 任务 = 一次提交**；禁止把多个任务或无关文件塞进同一 commit。
- 文档改动（GAME.md/TECH.md/BUILD_PLAN.md）随其所属任务的 commit 一起提交。
- 提交信息使用 §3(d) 格式；不 push 除非用户明确要求。

## 6. 交付格式（每次任务结束必须按此回答）

1. **改了什么**：文件清单 + 关键改动点（含本次更新了哪些文档小节，见 §2.5）；
2. **怎么验证**：验收命令/输出/截图，对应 BUILD_PLAN.md 的验收标准；
3. **对应任务编号**：BUILD_PLAN.md 的 `[Pn][L01-xx]`；
4. **下一条任务**：BUILD_PLAN.md 中的下一个任务是什么（一行即可）。
